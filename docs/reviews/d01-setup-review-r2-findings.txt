R3 - Medium: ordinary CLI cannot explicitly select its board credential
Location: setup.txt:351-352,395-405,454-460,489-496.
Accepted basis: slice01 04:17-33,101-109 and 05:25-44.

- Credentials are now stored per installation/board/incarnation/grant, with more
  than one actor/grant file possible. The contract says to load the exact file
  and forbids implicit actor choice for original lookup, but provides no ordinary
  board-command flag, private binding or explicit selection procedure that supplies
  G. --grant is defined only for credential issue/revoke; --native-owner selects
  the separate administrative capability. Accepted core CLI grammar uses --board.
- For example, issue credentials for a human grant and an automation grant on
  the same B/I, then invoke board read or operation read for the human's original
  evidence. There is no callable way to choose the intended board credential.
  Choosing the first/latest file risks unexpected actor attribution; refusing
  ambiguity without any selection path leaves the ordinary journey unavailable.

Bounded required correction:
- Define the explicit selection grammar or private credential binding for ordinary
  board commands, including which installation/B/I/G it resolves and what happens
  when absent, ambiguous, expired, disabled, wrong-incarnation or unavailable.
  A credential selector selects a credential; authenticated attribution remains
  server-resolved. It must not be an actor claim or implicit native-owner fallback.
- For original outcome lookup, require the selected credential's actor and exact
  installation/origin/B/I to match immutable evidence, with current read-own-outcome.
  Do not rewrite evidence, search another actor/installation automatically or replay.
- Name its existing C01/K02/K03/P01 owners and D01 acceptance gate as applicable.
  Add a two-actor/two-credential synthetic vector showing deliberate selection,
  ambiguity refusal, wrong-actor unknown/denial and no authority fallback.
