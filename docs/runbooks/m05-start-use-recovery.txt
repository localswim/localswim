M05 START, USE, STOP AND RECOVER
2026-11-04 | Synthetic Windows amd64 local review

Start with the M05.04 kit's localswim.exe. In PowerShell compare its SHA256 with
both the manifest and this qualified executable value; stop if either differs:

  $exe = 'C:\path\to\kit\localswim.exe'
  Get-FileHash -LiteralPath $exe -Algorithm SHA256
  # 34388dd5275c42ed407662c79cc09ce8b87bf8ddd86c185815a5695e01506d75

The executable embeds the browser application; ordinary use needs no Node/npm,
account or certificate. Keep the kit separate from private runtime data. Use a
new synthetic workspace and an unused port (8820 is an example; do not use the
administrative board's 8810). This is a local review kit, not real-data adoption.

  $demo = Join-Path $env:LOCALAPPDATA ('localswim\m05-demo-' + [guid]::NewGuid().ToString('N'))
  $workspace = Join-Path $demo 'workspace'
  [System.IO.Directory]::CreateDirectory($demo) | Out-Null
  & $exe serve --workspace $workspace --port 8820

Leave the foreground service running. In a second PowerShell window set the same
$exe, $demo and $workspace values. Create the project and boards once:

  & $exe --workspace $workspace project create --key harbor --label Harbor --root (Join-Path $demo 'harbor')
  & $exe --workspace $workspace --project harbor board create --key dispatch --label Dispatch --root (Join-Path $demo 'harbor\dispatch')
  & $exe --workspace $workspace --project harbor board create --key research --label Research --root (Join-Path $demo 'harbor\research')

Open the numeric-loopback address printed by the service, for example
http://127.0.0.1:8820/. Select Harbor / Dispatch; its route on that origin is
/board/harbor/dispatch. Read current board and wait for Current. Board selection
is explicit: equal display tickets on Dispatch and Research are different cards.
Use exact UUIDs for CLI commands, with global selectors before the command:

  $selection = @('--workspace', $workspace, '--project', 'harbor', '--board', 'dispatch')
  & $exe @selection --json board read
  & $exe @selection card relationships 'CARD-UUID-FROM-BOARD-READ'

Daily use
Create or edit cards with deliberate priority, owner and lane choices. P3 is
normal; relationships and hierarchy do not propagate these fields or grant rights.
Human approval follows the existing policy; the automation CLI cannot approve.
Open a card's Parent and Children section to create a child, choose or change a
parent, or explicitly clear it. Read current hierarchy when stale. Completed
sources are read-only; archived or Completed cards can be parent/relationship peers.

In Relationships, read current facts when stale. The five stored kinds and their
source meanings are: Depends on (blocking), Informs (informational), Related to,
References and Duplicates. Depends on points from dependent to prerequisite;
only a current nonarchived human-approved Completed prerequisite satisfies the
start gate. Duplicates is descriptive and does not merge cards. Incoming labels
are derived views of facts owned by the other card. Open the actual owner to edit
or remove its fact; replacing this card's owned set never changes incoming facts.

Create card/Create child can submit its optional parent and relationship set
atomically. Replace owned relationships starts with the complete owned set, not
just the displayed page; save commits the proposed set together. At most 100
entries may be submitted; invalid input refuses the whole operation. Explicitly
clearing the owned set retains incoming facts. Read current facts after changes.

Find cards supports text and filters; Active hides archived cards. Confirm Archive
on unfinished cards, select Archived or All to find them, and confirm Unarchive.
Read current facts and reapply filters. Tab visits named controls; Enter/Space
activates buttons, arrows operate selection controls. Single-line Enter submits
once, multiline Enter adds a newline, and IME composition does not submit. Escape
closes only the active unsubmitted editor; dirty input asks before discard. Closing
details restores the live opener or the board-read fallback.

Recover, stop and reopen
Wait for private recovery to save before leaving input. If storage fails, keep the
tab and visible input; a forced loss can lose it. A current read does not rebase
a draft. On conflict compare current facts and retained input before a deliberate
new operation. UNKNOWN may have committed: retain its immutable original and
source, and deliberately use Look up original outcome. Refresh, restart, search,
navigation and current-card reads neither settle nor replay it. Do not resend an
uncertain original or infer its outcome from current state.

Stop the owned foreground service with Ctrl+C and wait for clean exit. Reopen the
same workspace without repeating creation:

  & $exe serve --workspace $workspace

The saved port, board membership and identities remain. Refresh boards until
connected, reconnect the local service if needed, and read current board. Do not
bypass an active owner, edit data files or remove sidecars to repair a refusal.
Keep workspace, board data, service metadata/credentials, CLI evidence and browser
recovery private and outside the kit and public reports.

Current startup requires physical storage 7/base 5; it does not upgrade stores.
For a separate synthetic offline upgrade, stop the owner and follow the exact
identity, inspect and 5->6->7 procedure in docs/runbooks/m05-relationships.txt.
Uncertain postcommit outcome requires deliberate inspection, never automatic retry.
