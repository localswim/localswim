Local notices through the native CLI

Use the same running service, selected board and current authorization as for
ordinary board commands. Start with one of these prefixes:

  localswim --data DIR
  localswim --workspace DIR --project PROJECT --board BOARD

Add --json before notices for the versioned response. The readable output
shows the selected board and incarnation, state and reason, target, checkpoint,
cut information and any returned receipts. Notice records contain bounded
activity metadata.

  notices status
  notices configure
  notices start
  notices inbox
  notices lookup --target-id ID --delivery-id ID
  notices stop

Configure returns the selected incarnation's fixed target. Start opens that
target, including eligible catch-up after a clean stop. Inbox lists at most 64
retained pairs. Copy the exact target UUID and 64-character lowercase delivery
digest from the selected board's inbox or pending status for a deliberate
lookup. Accepted lookup can settle the exact pending notice. Unknown lookup
means the host could not confirm acceptance. Use status to see the current
checkpoint and any guarded pending delivery.

Configure, start and stop each fetch the current generation once and submit
once. CONTROL_STALE means another action or engine reopen changed the
generation. Read status, then decide whether to issue a new command.
CONTROL_BUSY means the action is refused in the current state.
If a submitted request returns OUTCOME_UNKNOWN, read status before deciding
on any further action. For lookup, preserve the original target and delivery
IDs and check the retained evidence. A partial drain retains ownership while
admitted work finishes. Check status for its terminal state. If capacity or storage is
reported, inspect status and the retained inbox before deciding how to proceed.

Exit 0 means a valid result was returned. Check its state and lookup evidence.
Exit 1 indicates invocation or local I/O failure, 2 a refused request or
credential context, and 3 an unavailable credential, service or validated
response. Exit 4 means a submitted request's effect could not be confirmed.
The CLI uses only the selected service API for notice data.

C1 verification uses the Windows amd64 executable built from the candidate.
Set M12_CLI_BINARY to that executable and M12_CLI_ROOT to a short, private
synthetic fixture parent. The test needs the default standalone port 8792
available and allocates other loopback ports for configured fixtures.

  go test ./internal/transport/cli/core -run '^TestNotice' -count=1
  go test -tags 'l02_native m11_cli_native m12_cli_native' ./cmd/localswim -run '^TestNoticesActualBuiltCLI$' -count=1 -v

The executable suite tests ordinary selection, catch-up and receipts, scoped
authority, stopped-host refusal and a controlled stale-generation race on a
real engine. The focused CLI suite exercises guarded lookup, capacity and
partial-drain rendering with controlled responses. Durable capacity and stalled
drain are exercised at the monitor/host boundary by the M12.03/.04 probes.
