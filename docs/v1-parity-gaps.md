# V1 functional parity gaps after T10

T10 delivers the planned V2 backend sequence. Full V1 functional parity still needs the live Attention workspace, several daily card and attachment interactions, the Bot's focused reporting workflows, and equivalent recovery and publishing safeguards. The largest gap for Terry is opening the workspace and immediately seeing what needs attention as work changes.

The baselines are V1 main at `46d5d58` and V2 main at `9dedae2`. The latter includes the `edb888a` T10 implementation and the final roster. This audit compares the shipped paths through the browser, CLI and service. It uses source and existing verification evidence, plus focused probes against the published Windows V2 binary with disposable data. [V1 baseline](https://github.com/TerryOtt/localswim/blob/46d5d58695aa807c246c42e45f0615860fdcbbe5/README.md) · [V2 baseline](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/execution-plan.md#L386) · [V2 parity remit](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/CONTRIBUTING.md#L3)

V2 already provides revision-checked card writes, archive and restore, typed links and hierarchy in the API, dependency priority and ticket ordering, individual and lane approval, attachment upload and verified download, native backup and restore, Git publication, board close and reopen, staged activation and graceful service stop. The gaps below describe the behavior still missing at the point where Terry or Bot uses those features. [Delivered milestone scope](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/milestone-plan.md#L42) · [V2 browser workflows](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/web/README.md#L148)

### Attachments and background work

V2 supports one selected file per upload on an existing card, verified preview and download, explicit cover selection and detach. V1 also accepts pasted screen clips in the drawer and New card dialog, and multiple files before card creation. It shows per-file progress and supports continuing pending uploads after partial success, with original-file reselection after reload. V1 shows the first image on a card when no explicit cover is set. V2 only renders an explicitly selected cover on the card face. A parity check should create one card with two files and a pasted clip, interrupt a later upload, then confirm that successful uploads stay attached and that continuing the operation preserves the original card and bytes. [V1 attachment workflow](https://github.com/TerryOtt/localswim/blob/46d5d58695aa807c246c42e45f0615860fdcbbe5/README.md#L558) · [V2 upload](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/web/app.mjs#L1103) · [V2 create form](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/web/app.mjs#L1884) · [V2 cover rendering](https://github.com/localswim/localswim/blob/9dedae22891d45ee6df24ae65b27c76150cb5900/web/app.mjs#L1720)

V2's backend captures a coherent backup while allowing later edits to continue. Its browser backup action runs under the shared write gate, which blocks normal navigation and other submissions in that tab until the action settles. V1 keeps the board usable during slow capture and publication. Qualify this from the same browser tab by editing another card while backup runs and verifying that the backup still contains the original captured revision. ## 3. Workflow setup and approval controls

- **Terry's board preset.** V2's default has five lanes and P2 Normal. V1 ships a separate Terry preset with Blocked, Needs Terry, P0–P5 with P3 Normal, Bot ownership, explicit actor grants, and its lane action opt-ins. V2 can create a custom workflow with explicit UUIDs, roles and ranks. It still needs a ready-to-use equivalent of the Terry preset and a way to configure the reorder opt-in. Also verify custom priority scores where V1 uses the numeric P suffix and V2 uses the configured rank. - **Lane action configuration.** V2 applies dependency order with a saved, revision-bound preview. The browser offers preview on every active lane, and lane PATCH rejects `reorder_enabled`. V2 uses the fixed approval comment for every card, caps lane approval at 1,000 cards, and has no equivalent of V1's configurable lane approval text. Its normal CLI has no approval command, while the REST approval route accepts Human authorization through either the browser capability or the Human API token. V1 reserves that action for its browser authority. The Human credential boundary is a product decision to reconcile. It renders stored `user_css` but normal create and patch provide no way to configure it. Align the advertised fields with the supported operations. ## 5. Recovery, isolation and publication

These gaps affect whether an operator can trust the same workflows on fresh V2 data.

| Case | Post-T10 result | Behavior to preserve |

## 6. Cutover boundary

Keep the approved one-port architecture, fresh V2 data, UUID addresses, dated REST contract, and Windows-first qualification. V1 migration, legacy schema upgrades, old CLI spellings and per-board gateway processes are outside the parity target. V1 automatic source reload is replaced by explicit staged activation. T10 qualified same-port replacement, credential refresh, failed takeover recovery and graceful stop on Windows. A repeatable independent startup and recovery procedure for the actual shared installation, including CLI credential setup and app reconnect after replacement, still needs a representative run. V1's detached gateway procedure is a behavior reference for that run.
