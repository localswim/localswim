## Implementation and verification

Durable health and ordinary write checks share a fixed 64-board validation-result
cache. Each check reads and hashes the current bounded file. A healthy result also
requires the final file identity, size and modification time check. Matching bytes
and accepted revision reuse the validation verdict. Changed content is revalidated
even when its size and timestamp are unchanged. A new accepted revision requires
validation and comparison against the saved bytes before it can reuse that verdict.
The cache keeps digest metadata and fixed verdicts only.
Catalog enumeration avoids cloning every board merely to collect its UUID.

The browser's confirmed-data cache retains its existing per-tab byte budget,
eviction, freshness and retry behavior. Full native verification, startup admission,
recovery validation and captured backup verification retain their existing paths.

`TestM94` checks unchanged-metadata damage, divergence and repair, file replacement
after a cached success, final-write admission, bounded cache replacement and
concurrent catalog reads during a commit. It also checks that successful commits
still require a durable comparison. `BenchmarkM94DurableValidation` compares
the full validation path with repeated cached checks on the same 60-card snapshot,
including file reads and reporting allocations.
