W03 ATTACHMENT AND EXPORT CONTROLS

ArchiveView reads current authenticated scope/board metadata and retains a separate
attachment editor's original base. It captures one private raw file buffer, computes
exact SHA-256/length, and saves metadata-only private drafts. The actual shared API
provider freezes semantic evidence in W01, awaits transaction completion/readback,
and only then dispatches exact multipart metadata/file. No raw file bytes or browser
path enters recovery. Unknown outcomes retain original identity for lookup only;
no automatic upload, replacement operation or replay exists after reload.

Private writes join the workspace's shared origin/database/installation clear
boundary at the edit event. Earlier metadata drains before clear; later deliberate
edits wait behind it and remain recoverable. A file read/hash begun earlier may
retain its visible selection but cannot automatically recreate discarded metadata
after the boundary. Attachment admission persists immutable evidence before clear
can advance; it never waits for a network outcome to admit private discard.

Downloads use exact authenticated bytes, verified SHA-256/length by the provider,
and forced application/octet-stream offers. H02 export bodies are completely
received with exact MIME/encoding/length bounds before a forced ZIP offer. The UI
does not duplicate A03's archive validator. Browser status is offered, destination
null, local save unverified. Cancel/incomplete/unavailable bytes never confirm a
local save. Exports and downloads cannot change a committed operation outcome.

No inline executable attachment rendering, browser restore, filesystem path entry,
detach/replacement, grants, trust enrollment or native bootstrap is present. All
labels/prose use inert text; explicit buttons and IME gates preserve input/focus.
V02's product browser/profile gate remains; synthetic component tests do not prove
real TLS/trust, native publication, eviction or power-loss behavior.
